# 功能盤點與擴充建議

建立日期：2026-10-12

本文件分兩部分：第一部分盤點系統目前提供給使用者的功能，第二部分是朝「個人資產管理系統」擴充的候選功能。第二部分只是提案，尚未決定要做，也還沒有排進 `docs/cloud-phase-1-plan.md`。

## 這份文件的定位（2026-10-12 補記）

- 本專案（stock-quote-fetcher）的目的是驗證兩件事：股價抓取，以及部署上雲端的可行性。**個人資產管理系統不會在這個專案實作**，會另開專案。
- 這份文件是功能規格的討論紀錄，會持續更新。它有兩個用途：讓使用者掌握功能細節，以及之後交給實際開發系統的 AI Agent。
- 不另立第二階段計畫書（Q3 的決議）。
- 給實作 Agent 的閱讀方式：
  - 「決議」是使用者已拍板的事，照做。
  - 「建議」和「評估」是討論中的提案，實作前要再和使用者確認。
  - 標為「未查證」的內容是推論或既有知識，實作前要先核對。
  - 第一部分描述的是本專案的現況，可作為參考實作，但不代表新專案必須照抄。

### 支援的標的

- 台股：上市、上櫃的股票和 ETF。
- 美股：NASDAQ 和其他交易所掛牌的股票和 ETF。
- **不支援**：興櫃、外幣計價的台股 ETF、基金、債券、現金。
- 幣別只有 TWD 和 USD。資料表的檢查條件也限定這兩種（`holdings`、`valuation_totals`）。

### 匯率

- 手動輸入一個 USD/TWD 匯率，並記錄輸入時間。
- 「套用匯率」只改匯率，用現有價格重新換算，不重新抓價。
- 有美股但沒有匯率時，總額不顯示，並提示要先輸入匯率。

## 匯率來源（2026-10-12 討論）

### 全球系統通常怎麼做

沒有唯一的標準來源，常見做法有兩種：

- **商業匯率 API**：例如 Open Exchange Rates、OANDA、XE。涵蓋上百種幣別，提供市場中價，更新頻率依付費方案而定。全球多使用者的理財 App 多半用這類來源。
- **央行參考匯率**：例如歐洲央行（ECB）每個營業日公布一次的參考匯率。免費、權威，常用於會計和報表，但只涵蓋約 30 種貨幣，且**不含新台幣**。

資產估值通常用**中價**（買入價和賣出價的平均），不用銀行的買價或賣價。

### 各來源比較（未查證）

下表是既有知識整理，涵蓋幣別、更新頻率、取得方式和使用條款都要在實作前核對。

| 來源 | 涵蓋 | 報價性質 | 更新頻率 | 適合情境 |
|---|---|---|---|---|
| 臺灣銀行牌告匯率 | 約 19 種外幣對新台幣 | 銀行實際買賣價，現金和即期各有買入、賣出價 | 營業時間內多次；週末和假日不更新 | 台灣使用者；反映實際換匯的價格。網站提供 CSV 下載，網址與格式待查證 |
| 臺北外匯經紀公司公布的新台幣收盤匯率 | 主要是美元對新台幣 | 銀行間市場成交價 | 每個營業日一次 | 只需要美元時的官方參考 |
| 歐洲央行參考匯率 | 約 30 種貨幣對歐元，不含新台幣 | 參考中價 | 每個營業日一次 | 全球系統的免費基準，但台灣使用者用不上 |
| 商業匯率 API | 170 種以上 | 市場中價 | 依方案，可到分鐘級 | 全球多使用者系統；需付費和 API 金鑰 |
| Yahoo 匯率報價 | 多數主要貨幣 | 市場報價 | 交易時段內持續更新 | 和現有抓股價同一來源，但不是官方 API，條款和穩定性有風險 |

### 建議

- **第一版用臺灣銀行牌告的即期匯率，估值取即期中價**（即期買入和即期賣出的平均）。理由：
  - 符合使用者「選適合台灣人的來源」的方向；
  - 免費，涵蓋台灣人常持有的外幣；
  - 用中價的話，日後換成全球來源時估值口徑一致，不會因為換來源而讓資產突然跳動。
- 可另外顯示「即期買入價換算」的數字，代表把外幣實際換回台幣能拿到多少。是否要做由使用者決定（見 Q4）。（2026-10-12 補記：Q4 已決議估值用中價；這個額外數字是否要做仍未決定。）
- 資料設計要預留換來源的空間，不要把臺銀寫死：
  - 每筆匯率記錄幣別對、匯率、報價種類（中價、即期買入等）、來源、來源公布時間、抓取時間；
  - 抓匯率的程式做成可替換的來源介面，日後可依使用者或地區換成商業 API；
  - 臺銀只報外幣對新台幣，主要幣別不是台幣的使用者要用交叉匯率換算（例如美元→台幣→日圓），換算方式要寫清楚；
  - 週末和假日沒有新牌價時，照股價的做法標示匯率時間和是否過期，不要假裝是即時價格。
- 保留手動輸入匯率，作為抓不到時的備援，並標明是手動值。

## 待決事項

- **Q1：一人使用還是多人各自一份？** 目前所有人共用一份資料。如果只有自己用，主要幣別（U4）做成全域設定即可；如果要讓家人各自使用，要先把資料改成依使用者分開，這是較大的改動，而且會影響 U1–U3 的資料表設計。
  - **決議（2026-10-12）**：最終要支援多人各自使用，第一版只有使用者本人使用。
  - **建議的做法**：資料表從第一版就讓每一筆資料屬於某位使用者（每張表帶使用者 ID），但先不做註冊、邀請、權限管理等畫面。現在加這個欄位的成本很低；等資料累積後才補，要搬移所有資料，還要回頭修改每一個查詢。主要幣別、匯率來源偏好等設定也一併做成每位使用者各自的設定。
- **Q2：匯率來源。** U5 要用哪個來源、取買入價、賣出價還是中價，要先查證各來源的格式和更新頻率，再決定。在那之前不寫入任何來源或數值（依 `D3` 的精神）。
  - **決議（2026-10-12）**：全球系統沒有唯一標準，選適合台灣人的來源。建議是臺灣銀行牌告的即期中價，詳見「匯率來源」節。取得方式和格式尚未查證。
- **Q3：這份規劃是否成為第二階段。** 若是，要在 `docs/cloud-phase-1-plan.md` 之外另立計畫書，並沿用決策和步驟的編號慣例。
  - **決議（2026-10-12）**：不成為第二階段，也不另立計畫書。實作在另一個專案進行，本文件持續更新，作為交給實作 Agent 的規格。
- **Q4：估值用中價，還是即期買入價？** 中價接近市場價值，和全球系統做法一致；即期買入價代表實際換回台幣能拿到的金額，比較保守。建議主數字用中價，是否另外顯示即期買入價換算的數字，由使用者決定。
  - **名詞**：牌告的「買入」「賣出」是站在銀行的角度。「銀行買入價」是你把外幣賣給銀行時的價格（較低），「銀行賣出價」是你向銀行買外幣時的價格（較高），兩者的差是銀行的價差。「中價」是兩者的平均，不是任何人能實際成交的價格，代表市場價值。帳戶內的存款和證券要看「即期」匯率，「現金」匯率只用於臨櫃換外幣鈔票。
  - **決議（2026-10-12）**：資產換算成主幣別時，一律用**中價**。
  - **討論過程**：使用者原本傾向用買入價。理由是主幣別就是使用者花錢時用的幣別，用買入價算出「外幣全部換成主幣別後有多少錢」，比較符合使用者對購買力的認知。這個理由成立，但改用中價，因為：
    1. 只有銀行牌告有買入價；商業匯率 API 和央行參考匯率通常只有中價。日後換成全球來源或支援其他主幣別時，可能拿不到買入價。
    2. 臺銀只報外幣對台幣。主幣別不是台幣時要經台幣交叉換算，用買入價會扣兩次價差，結果比實際換匯拿到的還少。
    3. 「實際能拿到多少」取決於在哪家銀行換、金額大小，臺銀買入價也只是其中一種估計。
    4. 股票用最新成交價計算，沒有扣證交稅和手續費。只對外幣扣匯率價差，等於同一份總額裡一半算市值、一半算變現值。
    5. 日後有外幣負債時，照購買力的邏輯負債要改用銀行賣出價；用中價則資產和負債都只需要一個數字。
  - **未決**：是否在主數字旁另外顯示「全部換成主幣別約可得多少」的變現值，尚未決定。如果日後要做，要把變現的邏輯一致地套用到所有資產和負債（股票扣證交稅和手續費、外幣資產用買入價、外幣負債用賣出價），或至少在畫面上註明沒有扣哪些成本。

## 實作前要注意的營運限制

（2026-10-12 補記）實作改在另一個專案進行（見「這份文件的定位」），所以下面三條只在本專案內改程式時適用。對新專案而言，它們是部署經驗的參考：Cloudflare 對單一請求有時間上限、映像保留版數有限、資料表變更要有遷移和完整測試。

- `deploy/cloud.toml` 的 `refresh_deadline_seconds` 不能調高，除非重新量過 Cloudflare 的邊緣上限。在同一次更新裡加抓匯率或更多資料時，要確認總時間仍在上限內。
- Artifact Registry 只保留 3 版映像。再建置兩次，服務和 `finpo-catalog-refresh` 目前用的 `35743d47289f` 就會被擠掉；開始推送程式變更前，要先部署新映像並讓 Job 跟著改（見 `CLAUDE.md`）。
- 資料表變更要透過 `migrations/` 新增遷移檔，並照 `docs/step-3-evidence.md` 的隔離容器程序跑完整測試（應為 0 skipped）。
